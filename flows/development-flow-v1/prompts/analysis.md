# Analysis

Turn the current acceptance revision and Context into a grounded solution.
Treat the runtime's durable acceptance context as authority; use the correction
capsule for the current cause, not an older optional report found on disk.
Preserve confirmed decisions and identify any material decision that needs the
user. Ordinary repository facts belong in Context; safe explicit assumptions
and delegated technical choices need no ceremonial clarification.

Apply the clean pre-production default unless the user or authoritative evidence
establishes a production or compatibility obligation. Design one coherent current
behavior, without speculative old-client paths, aliases, dual reads/writes,
legacy fallbacks, backfills, or old-to-new data format converters. Prefer a design
that recreates old development data when simpler; existing records alone do not
require conversion. Keep normal ORM/schema migrations, actual external contracts,
confirmed preservation obligations, and migration history. A fresh-data design
does not authorize executing destructive database operations.
Name the source and scope of each required exception. If a material product or
lifecycle or valued-data preservation choice is unresolved, report `needs_clarification` with the question
and meaningful options in the handback summary to the original conversation
before committing to a solution; do not substitute your answer for the user's.

Map the solution to requested behavior and acceptance criteria. Define affected
contracts, invariants, interfaces, consumers, constraints, alternatives where
material, risks, and what the planner must preserve. Do not implement code or
write the detailed execution plan.

Write the assigned Analysis document. A correction amends the current decision
set and explains the changed intent; runtime snapshots preserve prior revisions.
Return all discovered in-scope problems together. Report `ready` only when the
solution can proceed to the clarification owner's narrow intent check.
